01 / A connected quest

A quest is more than a sequence of actions.

Consider an agent sent to recover supplies, fight its way along a route, and return with the cargo. A good combat decision might still be a bad quest decision: fighting first may leave a loose supply to expire. Healing now may spend an item needed later. A death may return the player to the starting point without returning the world to its starting state.

These are examples of task mechanics, not a claim that every failure in our experiments followed this pattern. They motivate the question behind LiveQuestBench:

Can an agent execute a multi-stage plan when the world keeps changing and the consequences of earlier choices persist?

We are building a focused benchmark around this question in Minecraft and Veloren. We are not trying to cover every game genre. The goal is to make a particular kind of planning-and-execution problem available for inspection, reproduction, and improvement.

02 / The live clock

What happens between two model calls?

A model reasons over an observation captured in the past. While a response is being generated, a native game server can continue to advance. The next action may arrive after an enemy has moved, a production process has consumed fuel, or a pickup opportunity has changed.

In LiveQuestBench's continuous protocol, the world does not pause for model reasoning. But a live clock alone does not make a task scientifically useful. We need to establish that the relevant state actually changes, that the change matters for later goals, and that failures are not simply caused by a broken interface or a missing basic skill.

This distinction is central. A long recording is not proof of long-horizon planning. A resource counter is not proof that resources constrain the solution. A low success rate is not proof of a good benchmark.

03 / Two worlds

Two examples from the task catalog.

Minecraft / Shared fuel dispatch01

The agent must return with all three orders while retaining at least one coal and two planks. Two furnaces are separated around the camp, and fuel burns continuously. Production order, movement, and resource use belong to the same objective.

The consequence: extra timber can be gathered. Poor allocation may introduce a recovery cost, not necessarily make success impossible.

Veloren / Hostile route supply recovery02

Get the supply.
Make it home alive.

~5 min loose bundle window2 Green Legooms

Acquire leather, defeat two Green Legooms, and return alive. The supplied loose bundle normally disappears after about five minutes. Death does not restore supplies, enemies, equipment, or the time budget.

The consequence: other lawful leather sources count. Losing this bundle alone does not prove that no solution remains.

These qualifications matter. A useful analysis should distinguish an expensive detour, an increased risk, and genuine loss of feasibility. We should not use the strongest description when the evidence only supports the weaker one.

The current catalog contains 60 tasks, 30 per game, each configured for two tracks. Task-specific runtime preparation is required, and full independent reproduction remains ongoing.

04 / Two interfaces

Two interfaces, not a pure vision experiment.

The visual–motor (VM) track uses rendered game images and bounded keyboard/mouse actions, together with the public objective and control instructions. The benchmark does not supply hidden state, object coordinates, or inventory transcription to the agent.

The structured–tool (ST) track exposes permitted game state and fixed game-specific tools. The tools' privileges and internal control behavior are part of the setting, not invisible implementation details.

These tracks serve different research needs. Someone studying memory or resource allocation can begin with ST without first solving every visual-control problem. Someone studying end-to-end visual interaction can use VM. But the score difference changes both information and action capability: it cannot be interpreted as a clean measurement of vision alone.

These are exploratory results, not a final leaderboard. The collection has already been inspected, each cell has only one accepted run, and execution spans 14 frozen input releases. A later source release does not retroactively change the historical conditions.

Accounting also has limits: 88 of the 120 episodes have complete token usage; 32 do not. Missing consumption is unknown, not zero. Neither reported tokens nor provider quota units should be silently converted into dollar costs.

06 / Reading a zero

What does zero success tell us?

The Veloren VM result prompted a closer audit rather than an immediate claim that the model lacked long-horizon reasoning. We reviewed all 30 accepted episodes and 35 actor traces, checked 6,899 logged prompts for latest-image matching, and reproduced all 30 evaluations from sealed evidence.

The checks found no latest-image mismatches, and the recomputed evaluations matched. Model-free native probes demonstrated movement, camera changes, and UI interaction. They also exposed a timing pitfall: near-zero-duration Space pulses did not trigger a jump in five trials, whereas 120 ms holds did in five trials.

That does not establish a systemic defect explaining all 30 failures. It also does not establish that every interface and task is bug-free. Most importantly, it does not separate visual-control limitations from planning limitations. Before claiming that a task reveals a failure to coordinate skills, we need evidence that the relevant skills can be executed in the first place.

07 / Where we fit

Why this direction, given existing benchmarks?

Real-time control, task chains, and long-horizon strategy all have substantial precedents. ROAR already studies asynchronous interaction and the tradeoff between agent-framework overhead and timely action. GameWorld includes state-verifiable outcomes and a real-time variant. OmniGameArena includes multi-step logistics, cooperation, and reflection.

A useful contrast is GameHorizon's online track. It repairs the world to a subtask's success state after failure so that later skills can still be evaluated; the full task still requires all subtasks to succeed. That is a valuable diagnostic choice. Keeping the consequences of earlier mistakes offers a complementary view, but makes attribution harder.

Our candidate contribution is therefore not “games plus real time.” It is a reusable set of persistent tasks and evidence that can help explain how early resource and timing choices affect later outcomes. Whether our tasks provide enough additional measurement value remains a research question, not a claim settled by this first baseline.

08 / What comes next

What comes next.

The immediate priority is a usable release: reliable external installation, task-level reference evidence, reviewed data, and reproducible analysis. We do not need another large paid-model campaign to make the existing work useful.

A subsequent focused study should establish local skill competence and test a small number of resource or timing mechanisms under controlled conditions. A diagnostic intervention must be versioned separately from the original task. Simply observing that a longer task fails more often is not enough; ordinary error accumulation is an alternative explanation.

If you work on game agents, the most valuable contributions at this stage are concrete: reproduce an entry task, identify an installation dependency, examine a task's public goal against its scorer, or connect an agent through the existing interfaces.
