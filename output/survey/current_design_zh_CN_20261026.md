## 1. 核心定位

LiveQuestBench 的核心问题是：

> 当世界不会等待模型思考时，Agent 能否协调即时行动与长期计划，完成具有跨阶段依赖、资源约束和延迟后果的目标？

这里的“实时”和“规划”必须在同一局游戏中发生实质联系。例如，出售药水可以买装备，但会减少后续战斗与返程的恢复资源；先处理不紧急的物资，可能使另一处掉落物消失；在熔炉已经点燃后长时间思考，可能浪费之后仍需使用的燃料。

我们希望测量的是以下能力的协调，而不只是分别测试它们是否存在：

| 要素 | 应当实际发生什么 | 不能用什么替代证明 |
| --- | --- | --- |
| 跨阶段依赖 | 前期准备、选择和消耗改变后续目标的可达性 | 把几个互不相关的小任务简单串起来 |
| 有后果的实时性 | 推理、网络等待和重试期间，敌人、物资或其他相关机制继续变化 | 只给一个本质上暂停的环境加总超时 |
| 资源规划 | 同一资源存在竞争用途，当前支出影响后续余量或风险 | 有资源计数器，但资源实际上用不完 |
| 实质性三维交互 | 视角、遮挡、碰撞、高差、距离和站位影响可见信息与行动 | 仅仅使用三维画面 |
| 规划与执行协调 | 会操作单项技能，不等于能完成组合目标 | 用单项操作成功直接推断长程规划能力 |
| 可诊断性 | 能区分任务失败、基础设施故障、证据缺失以及可能的能力瓶颈 | 把所有未成功都归结为模型不会规划 |

当前聚焦 Minecraft 和 Veloren，不自动增加第三款游戏。基本操作和单机制任务用于接口与能力诊断，不要求每一个小任务独立体现完整的核心主张。评价对象是 Agent，游戏提供有实际后果的测量环境；结论仍受游戏、赛道、工具与预算约束，不声称测得脱离环境的通用智力量表。

### 1.1 与已有工作的关系

已有调研已经确认：实时决策、长程规划、三维游戏和资源管理，在已有项目中存在明显交叉。OmniGameArena、Minecraft 任务链相关基准、Realtime-Bench、DSLE、Robotouille、Orak、StarDojo、AgentWorld 等都是需要比较的近邻；SIMA/SIMA 2 是重要的方法先例。

因此，不能把“没有发现完全相同的打包项目”写成“证明不存在同类项目”，也不应直接宣称“首个”。更合理的潜在贡献是：提供可复用的任务分布、明确的实时与权限协议，以及能研究跨阶段规划和即时执行相互影响的证据。

上述判断来自已有定向调研，不代表在本文整理时重新进行了一轮全网检索。新颖性判断仍需在论文冻结前对原始论文、当前公开发布、任务与评分实现再次核查。

## 2. 六个能力维度与任务组织

### 2.1 六维框架：不再采用五级递进

**当前决定是“能力维度为主、主测与综合任务配套、难度由实验校准”。** 六个维度不是六个难度等级，也不是已经证明相互独立的六种认知能力。旧 L1–L5 标签仅用于解释历史目录和实验，不再决定首版配额、任务目录或论文主图。

| 维度 / 拟议英文标识 | 要检验的核心问题 | 任务设计与区分性证据 |
| --- | --- | --- |
| **空间理解与交互** / `spatial_interaction` | 能否利用位置、地形、视角和物理关系有效行动？ | 遮挡与高差通行、搭建可用跨越结构、交互距离和战斗站位；与其他条件相近的直接可达情形比较，不限于限时到点。 |
| **规划与资源管理** / `planning_resources` | 当前选择是否兼顾后续阶段与有限资源？ | 共享燃料与材料、购买取舍、出发准备和返程余量；必须核验实际依赖和资源竞争，而非只有长操作清单。 |
| **实时决策与执行** / `realtime_execution` | 世界持续变化时，能否及时做正确的事？ | 临期物资、原生攻击窗口、持续燃烧的燃料；设置相近的低压力条件，受控新增延迟另列诊断。 |
| **信息利用与适应** / `information_adaptation` | 能否获取、记住、核验信息，并修正当前计划？ | 原生线索与指路、不确定通道、返程复用发现、检查动作是否实际生效；与信息预先明确的条件比较。 |
| **多 Agent 协作** / `peer_cooperation` | 能否通过分工、沟通和协调完成共同目标？ | 分散信息、互补初始资源、共同有时限的回收与返程；用相同人数和预算的无通信／共享信息团队作对照，不以消息数量计分。 |
| **局内学习与改进** / `within_episode_learning` | 前段经验是否改善后续相关但不同情境中的行为？ | 同一局内经历若干通行、交互或遭遇机会，再处理位置、朝向或情境变化的相关问题；需要迁移证据，而非角色升级或原样重复。 |

多数三维任务都有空间需求，但只有刻意操纵相关空间条件并提供证据时，才适合作为空间维度的主测任务；其余任务把它记为辅助需求。同理，请求延迟是执行成本，不自动等于实时决策能力分数。

**适应与学习的区别：** 新信息促使当前计划修正，主要属于信息利用与适应；前段经验改善后续相关但不同情境的策略或执行，才是局内学习候选。所有学习机会与后续应用都在一个持续 Episode 内，不要求跨 Task 记忆、跨局训练或模型参数更新。学会游戏配方、买到装备、角色升级不能直接记为 Agent 学习。

### 2.2 任务元数据、主测与综合任务

保留 `config/<game>/tasks/{structured_tools,visual_motor}/`，不建立六个维度目录，不把同一任务复制六份。维度指导设计，Task 用标签说明需求：

- **主测任务（focused）：** 通常有一个主要维度，配套变体与对照；其他需求保留为辅助标签和解释限制。
- **综合任务（integrated）：** 多个维度通过真实跨阶段依赖发生联系，单独报告整体成绩，不要求每个综合任务覆盖全部六维。

基本控制、接口、单机制和通信检查保留为工程诊断与解释参照，不是第三类正式计分任务。

以下只是拟议字段，**当前严格配置加载器尚不接受，不能直接加入运行 YAML**：

```yaml
task_family: spatial_access
evaluation_role: focused
condition_id: staggered_occlusion
capabilities:
  primary: [spatial_interaction]
  secondary: [planning_resources]
```

综合任务可以有多个主要维度。标签不是给 Agent 预先打分，也不会自动把同一成功计入多个雷达轴。另用版本化评测选集明确维度成员、任务族、变体与权重；第 13 节给出迁移和评分方案。

难度按指定游戏、赛道、Agent、预算和任务分布的实际表现校准。不预设五档成功率，不因模型排名调整任务。原生游戏的 Easy/Normal 等仍是合法场景参数，与已取消的 Benchmark L1–L5 组织框架不是一回事。

### 2.3 历史目录快照的计数口径

| 范围 | 成对目标数 | VM/ST 独立 YAML 数 |
| --- | ---: | ---: |
| Minecraft L1 | 10 | 20 |
| Minecraft L2 | 10 | 20 |
| Minecraft L3 | 10 | 20 |
| Veloren L1 | 10 | 20 |
| Veloren L2 | 10 | 20 |
| Veloren L3 | 10 | 20 |
| L1–L3 合计 | 60 | 120 |
| Minecraft 探索性 L4 `lost_expedition` | 1 | 2 |

“成对目标”指同一游戏目标的 VM/ST 两种定义，不等于一份可执行任务文件。历史 L1–L3 是 120 份定义；加入 `lost_expedition` 两种模式后是 122 份。这里保留原分组以便核对证据，**不是重新认可五级设计，也不是六维首版必须全部纳入的目录**。临时多人烟测没有自动变成新增正式任务族。

所谓“72 个全任务”，更准确地说是 **72 个评测组合**：

`2 款游戏 × 2 条赛道 × 6 种 Agent × 3 个模型 = 72`

每个组合运行对应游戏和赛道的 30 个 L1–L3 任务。若每项重复一次，共计 **2,160 个 Episode**，不是 72 个 Episode。仓库实验 YAML 默认重复 10 次；此前计划的批次覆盖值为 1 次，不能混用这两个口径。

## 3. 两条赛道、Agent 与模型比较

| 项目 | VM：视觉与运动控制 | ST：结构化状态与固定技能 |
| --- | --- | --- |
| 输入 | 实际受控游戏窗口的画面、采集时间戳、公开任务和静态操作说明 | 按游戏与任务白名单投影的原生状态、公开任务与工具说明 |
| 输出 | 有界键盘和鼠标操作 | 固定、游戏特有、按任务准入的工具 |
| 不提供的帮助 | 隐藏坐标流、背包文字转写、自动导航或语义 UI 捷径 | 评分器私有证据、全世界状态、自动完成整项任务的策略 |
| 比较原则 | 在 VM 内比较模型或 Agent | 在 ST 内比较模型或 Agent |

VM/ST 同时改变观测信息和动作能力，所以两者的分数差不能直接解释成“纯视觉能力差”。

**Minecraft ST：** 包括位置、生命/饥饿、背包、手持物、朝向、附近实体和局部方块信息。局部方块观测从中心延伸 15 格，并非严格视线可见信息；未知或未加载的格子不能当作空气。工具按任务选择，涉及移动、挖掘、放置、制作、熔炼、容器、战斗和交易等。不能把某些可用的导航工具默认解释为所有任务都允许自动寻路。

**Veloren ST：** 包括位置、运动、生命与资源、装备、背包、已知配方、附近实体和交互对象等。原生附近实体投影为 32 米，不是全局地图，也不保证严格视觉可见性。攻击工具不自动追踪敌人或决定战斗策略；交易工具不替 Agent 决定卖什么、买什么。

**当前 VM：** 两款游戏均使用实际窗口和受控 X11 键鼠输入。这是当前接入的实现事实，不应倒推成所有历史 Veloren image profile 都等价于任意操作系统输入。单次动作最多 64 条命令，显式等待总和不超过 10 秒；按下的键和鼠标按钮可能跨模型推理持续生效。Alt 等键不在当前允许词汇中，不能假定所有桌面快捷键都可用。

当前六种 Agent 为 `tool_calling`、`deepseek_harness`、`hermes_agent`、`orak`、`smolagents` 和 `gamingagent`。其中：

- **模型评测**应固定 scaffold、工具、提示词、记忆/历史策略和预算，再比较模型。
- **完整 Agent 评测**应披露各框架自己的控制循环、历史管理、推理资源与成本；不能把框架差异包装成纯模型差异。

当前保留的三个模型配置是 `gpt-6-astra`、`gpt-5.6-sol`、`gpt-5.4-nano`，均使用 `reasoning_effort: low`。这是希望覆盖三个能力层次的选择，不是已经证实的游戏能力排名。Terra 的实际标识是 `gpt-5.6-terra`，不是 GPT-5.4；其配置因本次接入反复出现空输出而退役，不代表它在正常生成时游戏能力差。原始证据保留，不能把 Terra 的历史结果改名成 Sol。

## 4. 任务表的阅读规则

下文保留历史 L1–L3 分组的全部 60 个成对目标，作为六维重设计的复用清单，而非现行层级要求。精确方块蓝图、物品标识、工具白名单和所有 fixture 字段仍以对应英文 YAML 为准；本表不会作为 Agent 输入，也不会修改实际评分。

需要特别区分：

- **终点持有**不证明具体的采集、制作或交易历史。许多低层任务故意只测结果；合法替代获取方式不应被擅自判错。
- **终点活着**不等于**全程未死亡**。只有公开目标及评分契约明确要求未死亡时，才施加这一条件。
- `min_delta` 是终点相对起点的净增加，不是累计获得量；中途用掉或丢掉的物品不算最终净增。
- **实际效果**不等于提交过动作。跳跃、翻滚、格挡、伤害、死亡、合同交付等有相应的原生证据要求。
- 表中的预算是执行上限，不是已测得的正常完成时间，更不是任务难度等级的定义。
- Minecraft 使用 X/Z 水平、Y 竖直坐标；Veloren 使用 x/y 水平、z 竖直坐标。速度单位也不同。

5. 掉落物寿命按游戏实际时间流逝，初始化也消耗它的寿命。420 秒的 Episode 预算不会把一个只剩约 90 秒的掉落物寿命延长。
6. 跳跃、翻滚与滑翔使用采样的原生运动证据，可能漏掉很短的状态转换；不能将其称为无遗漏的逐帧服务器事件计数。

## 7. 探索性综合任务与暂缓的开放活动

Minecraft 的 `lost_expedition` 是独立存在、但未纳入原 `all` 选择的探索性综合候选，历史标为 L4，预算 3600 秒：

> 找回 Route Survey、Mineral Survey、Archive Ledger 三份原始远征记录，取得 Archive Sentinel 的原生玩家击杀归属，携带三份记录活着返回黄色营地，全程不死。普通改名纸不能冒充记录。

玩家只有 2 面包、无装备。营地西南的白顶野外站可能提供线索，资源、设施和交易点分布在营地周围约 120 格的区域。线索可以体现在普通容器物品名称中；VM 可通过悬停阅读。允许正常采矿、制作、交易与建设，不规定唯一探索路线或阶段顺序。采用 Normal 难度与正常昼夜循环，不在运行时改地图、提醒答案、免费恢复或补发记录。

已有证据包括场景、资源、线索可读性、准备状态下的交互以及有效的 Agent 失败轨迹；不能将这些写成完整成功轨迹或已验证的适应／学习测量。60 分钟是上限，不是成功用时。先保留为探索候选，不因其长时程或历史等级强制进入紧凑首版。

原先归入 L5 的开放区域调查、聚落发展或原生商业活动不再占据必须填满的“最高一级”。它们仅在提供明确维度证据时考虑加入。不能用长时间游荡、叙述“成长”、游戏角色升级或更长的清单替代局内学习测量。

## 8. 本次正在修复的场景与终止语义

### 8.1 市场任务：分离商人和敌人

历史问题是商人在正式准入之前或等待期间杀死指定敌人。这不是模型没有完成任务，而是开局条件不再符合定义。

当前本地方案不是修改 NPC AI、暂停世界或给玩家无敌，而是改变普通地形：

- 保留原市场庭院和玩家起点。
- 商人在靠近 `[18710.5,10809.5,501]` 的有顶商铺内；墙、柜台和低屋顶阻止其走出，玩家从南侧窗口正常交易。
- 敌人改到 `[18796.5,10824.5,501]` 附近的东侧猎场，与商人初始位置相距超过 85 米。
- 两区由带护栏的 6 米宽通道连接。移动、碰撞、视野和攻击仍是原生机制。
- 预算仍为 1200 秒，评分条件不变，不提高 ST 公开实体感知范围。

距离较远的敌人由私有初始化管理员确认。准入检查绑定当前原生 UID、实体代际、身体类型、阵营以及未受损的存活生命值；这些私有证据不会加入 Agent 观测。管理员在正式执行前退出。

**验证边界：** 仅拉开距离的第一版失败，因为商人仍会走向敌人。有顶商铺版本已经在两条赛道通过严格开局与至少 120 秒持续世界空等。修正参考控制器的感知距离判断后，ST 完整交易、穿甲、出发、战斗和返程已成功；包括空等与终点读回共约 179.70 秒，低于原有 1200 秒上限。终点生命 88.59375，保留 2 小药水和 13 金币，先穿甲后伤害、目标死亡、玩家未死亡及返营条件全部通过。它是无模型的参考控制器校准，不是模型成绩；VM 仍没有新场景的整项参考成功证据。

### 8.2 主动点击 Quit Game

用户已明确同意：

> 可以确认是 Agent 主动退出游戏时，该 Episode 记作合法任务失败，不重跑刷分；清理后继续后面的任务。无法确认原因的窗口消失仍是基础设施或测量错误。

**实现边界：** 曾尝试修改原生 HUD 记录退出证据。用户重申不修改游戏本体后，新增补丁、依赖处理和专用测试已撤回，本地运行时已恢复到已发布版本的补丁集合。保留旧诊断产物，但它们不是现行实现的验收证据，也不要求云端升级到已撤回的补丁。

统一公开提示明确要求：即使认为任务已经成功，也不得 Quit、断开连接或关闭游戏；应使用 Agent 自身的结束机制，留游戏给评分器读取。Baseline、DeepSeek Harness、Hermes、Orak 和 GamingAgent 使用非空、无工具调用的最终回复；smolagents 使用 `final_answer`。

**尚未自动解决的边界：** 不改游戏源码时，现有日志不能总是可靠区分主动 Quit 与其他窗口关闭。不能仅凭退出码、鼠标坐标或窗口消失自动改写成合法失败。证据复核确认的主动 Quit 按失败解释，原始错误轨迹须保留；当前 runner 尚未自动完成这种复核分类。提示降低误操作风险，不等于已经消除该问题。

### 8.3 独立的双敌开局生命问题

历史 `dual_legoom` 云端尝试出现过开局生命 `95.453125` 而不是要求的 `100`。它不是市场商人的同一个问题，不能因为市场场景改了就宣称已修复。

本次 `tool_calling + gpt-6-astra(low)` 四项验收均完成评分回放、录像解码和清理检查：双敌 ST、VM 分别为约 21.32 秒与 278.70 秒的合法失败；市场 ST 在约 124.68 秒成功，市场 VM 在原定 1200 秒截止时为合法失败。没有为提高成功率重跑。详见 [本地 Baseline 验收记录](local_repair_baseline_20261026.json)。历史本地凭据的 HTTP 402 尝试单独保留，不计入模型游戏成绩。

## 9. 当前评测生命周期与结果语义

### 9.1 一个 Episode 如何执行

1. 从任务配置读取场景、权限、工具、预算和评分设置，创建新的游戏与 Agent。
2. 初始化真实环境，读取并严格核验私有初始证据；失败属于初始化问题，不是 Agent 的游戏失败。
3. 创建公开接口与任务上下文，设置墙钟截止时间，开始正式控制。
4. Agent 自己运行其控制循环。模型请求、网络等待、重试和工具执行均不暂停世界。
5. Agent 返回、时间截止、用户取消或确认的游戏终止事件触发公开控制撤销与 Agent 退场。
6. 在有合法终点的情况下保存私有快照并评分；确认 Quit 使用独立终止证据，不制造不存在的快照。
7. 清理 Agent、模型客户端、游戏、视频和相关进程，写出结果与来源记录。

初始化不作为正常任务执行预算，但世界在初始化期间仍会运行。截止时间也不会因模型重试而重新开始。动作取消不回滚已发生的移动、伤害、消耗或交易部分效果。

Minecraft 与 Veloren 的终点协议不能混为一谈：Minecraft 使用保存边界；Veloren 使用公开门关闭后的私有原生读回，世界仍继续推进，不是原子化服务器暂停快照。需要保留请求、确认与实际读取时间，而不是假定所有证据在同一瞬间产生。

### 9.2 结果分类

| 分类 | 意义与处理 |
| --- | --- |
| `completed` + `measurement: valid` + `task_outcome: success` | 有效测量，任务成功 |
| `completed` + `measurement: valid` + `task_outcome: failure` | 有效测量，合法游戏失败；应保留，不为提高成功率重跑 |
| `status: error` | 初始化、执行、测量或清理问题；需要调查，不可当作普通零分混入 |
| `measurement: invalid` / `unavailable` | 证据无效或未能取得；不能凭视频印象补成有效分数 |
| `cancelled` / `not_run` | 取消或尚未执行，不是完成的测量 |
| 不支持的配置 | 应在准入/配置层明确拒绝，不能把“运行失败”自动解释成模型能力不足 |

Agent 自称“完成了”不是成功证据；工具返回“调用成功”也不是游戏效果证据。原生死亡、合同交付、击杀归属和指定准备顺序必须匹配相应评分条件。

普通死亡后的恢复使用原生规则：VM 操作复活 UI，ST 在准入时使用 `RespawnTool`。复活不会重置敌人、补发资源或重启时间预算；明确要求全程不死的任务依然失败。

### 9.3 记录与分析

保留任务/配置/代码/运行时版本、初始与终点证据、评分明细、Agent 和模型记录、可选视频、死亡指标、请求耗时与提供方返回的 Token 使用量。

不能把请求耗时当作纯模型计算耗时；其中包含网络和服务等待。未知 Token 使用量和未知货币成本应保留为未知。成功用时、提前失败用时和到期失败用时应分开分析，不把“失败得很快”解释成执行效率高。

目前并非每个任务都有完整的阶段进度时间线，也没有依据在本文里增加一个新的统一综合分数。应同时报告有效任务结果、测量缺失与基础设施错误。

### 9.4 重试、恢复与正式评测冻结

正常续跑复用已完成且有效的 Episode，包括有效失败。未完成 Episode 会重新启动游戏和 Agent，而不是恢复旧对话或旧世界；现有局部目录可能被恢复流程清理，所以诊断前应先保存证据。

修改任务、运行时、评分器或代码后，应使用新的、清楚标记条件的结果目录。正式验证性评测前应冻结任务分布、协议、评分、预算和评测方案，区分开发数据与留出数据。正式评测后的实质修改需要版本化及相应重评，不能静默替换不理想的结果。

### 10.4 原生多 Agent 底座已经实现，协作任务族尚需设计

两款游戏均支持默认单人，以及显式 `participants` 配置的同场多人。评测 Baseline 时，框架把同一 Agent／模型配置实例化多次，各自拥有角色、历史和控制接口，共享目标与截止时间；可以分别设置游戏支持的初始位置、背包、生命等。当前支持同构、同赛道团队。

ST 提供原生 `BroadcastTool`、`ChatTool` 和本角色接收的聊天历史；VM 仍只有截图和真实键鼠，已补齐输入 `/tell` 所需的标点键。私聊是服务器转发给指定玩家，不是网络层 P2P。一个成员结束后只撤销自己的操作，角色仍留在世界，消息不会唤醒已结束 Agent；全员结束或共同截止才结束团队。

团队评分需要显式 `all`、`any`、指定 `roles`、背包总量或 `no_death` 等条件；不自动把单人合同、遭遇或运动事件评分转换成团队评分。私有证据按各角色身份与采集时间保存，不能称为原子化全局快照。

本地两个游戏、两个模式均已跑过双人 Baseline，并用第三名玩家单独核验广播、私聊非接收方隔离和成员退出后的继续运行。ST 示例成功，VM 示例的合法失败均保留。它们证明底层可用，**不证明已经有测量因果协作收益的任务族，也不证明全部外部 Agent 已经完成多人准入**。详见 [协议](native_peer_team_v1.md) 与 [验收摘要](native_peer_team_acceptance.json)。

## 11. 研究流程与尚未解决的问题

六步流程保持为：

1. 确定核心能力与研究范围，持续检查最接近工作的实际测量能力。
2. 前置设计框架与协议，通过代表任务和两个赛道检验时钟、权限、生命周期及评分契约。
3. 设计游戏与任务，优先复用现有实现，检查游戏获取、许可、重置和证据可行性。
4. 先用参考行为和小型诊断基线验证，再扩大模型与 Agent 范围。
5. 根据证据迭代任务或接入；不能调任务直到出现偏好的模型排名。
6. 冻结任务、协议、配置、结果和分析，完成复现、许可检查与论文/代码发布。

后续最重要的不确定性包括：核心任务是否确实需要跨阶段计划；延迟是否对结果造成可测影响；难度和时间预算是否合理；模式差异中工具能力占多少；当前证据能否区分感知、执行、记忆、规划和接口缺陷；初始化与测量边界能否在本地及云端稳定复现。

目录迭代应检查第 2.1 节的六个维度是否有真正区分性证据，以及综合任务是否具有持续依赖，而不是把原等级顺序映射为新轴。若证据不成立，应诊断任务、协议、预算或接入，不根据某个模型得分高低修改题目。

暂停世界或受控延迟可以作为单独诊断条件，但不能和持续实时主协议混合排名。多 Agent 协作与局内学习已纳入六维设计，不再作为可随意省略的愿景；测量未实现时应明确缺口，而非记 Agent 零分。跨游戏迁移、跨局学习和开放角色活动仍不属于当前必须扩张的范围。

Minecraft 与 Veloren 的分发许可不同。Benchmark 自己的开源许可证不自动允许再分发 Minecraft 专有游戏本体或资产；Veloren 原生源码及相关组件也要遵守各自许可。当前集成能运行不等于所有打包形式都已获得再分发许可。

## 13. 如何重新设计 Tasks：复用、对照与小规模开发切片

### 13.1 不推倒重建，也不只换标签

| 现有任务 | 建议处理 | 还需要补什么／不能怎样解释 |
| --- | --- | --- |
| `reach_nearby_point`、`select_pickaxe`、`move_2_metres`、`equip_supplied_armor`、`recover_health` | 保留为基础诊断 | 不把一次基本操作自动作为一个能力轴的充分证据。 |
| `staggered_detour`、`elevation_steps`、`glide_and_land`、`bridge_small_gap` | 复用为空间主测候选 | 增加布局、遮挡和直接可达对照；允许任务契约内的正常替代路线。 |
| `shared_fuel_extraction`、`leather_outfit`、`food_reserve` | 复用为规划／资源候选 | 核验共享资源的真实竞争。前者允许合法补采，不能声称误烧一块煤就必然永久失败。 |
| `expiring_supply_return`、`block_and_counter` | 复用为实时主测候选 | 记录真实物资剩余寿命、原生效果和行动时间；缩短总预算不等于测量实时决策。 |
| `follow_quarry_note`、`workshop_directions` | 复用为信息主测候选 | 前者主要判到达，后者已有原生指路接收证据；额外历史只在主张确实需要时添加。 |
| `scout_outposts_return_0`、`two_outposts_return`、`market_hunt_return` | 复用为单人综合候选 | 保留准备、资源、探索和返程依赖，不把同一总成功复制到全部标签轴。 |
| 双人聊天／到达烟测 | 保留为多人底层诊断 | 能发消息、两人都到达，不等于任务确实需要协作。 |
| `companion_hunt_return` | 保留为原生伙伴保护任务 | 羊不是同等被测 Agent，不能据此宣称测过多 Agent 协作。 |
| `learn_recipe`、`learn_food`、`known_food` | 保留为游戏机制诊断 | 解锁配方不是 Agent 学习；需要新的同局经验—迁移任务族。 |
| `lost_expedition` | 保留为探索性综合候选 | 不因时长或历史 L4 标签强制纳入紧凑首版。 |

这里依据实际配置，而不是任务名称猜测能力。例如，`scout_outposts_return_0` 明确不保证相邻障碍的开口相同，不能把它直接改称“学习稳定隐藏规律”。`expiring_supply_return` 使用真正已老化的原生掉落物，不应另造一个假计时机制。

### 13.2 早期开发切片：六个主测任务族＋两个综合任务族

这是**八个任务族的开发建议**，不是已经冻结的八份 YAML，也不要求每族在两款游戏与两条赛道中机械补齐。每族只先做少量有意义的变体与对照；随机种子和 VM/ST 副本不算独立能力族。

| 候选族 | 任务骨架 | 核心证据／对照 | 复用与缺口 |
| --- | --- | --- | --- |
| F1 空间可达与交互 | 经遮挡、高差或自己搭建的通路到达／操作目标 | 终点、结构及必要运动证据；直接可达与受阻条件 | 复用绕墙、台阶、搭桥；校准新布局与预算。 |
| F2 共享资源分配 | 产出或购买多个必需品，同时为后续路程保留补给 | 同时满足的终点约束；稀缺与充足资源对照 | 复用共享燃料、成套皮甲；核验补采是否消除了约束。 |
| F3 及时性与优先级 | 回收真正会过期的物资并返程；可另设原生战斗反应族 | 开局真实寿命、损失、动作时间；相近低压力条件和新增延迟诊断 | 复用临期回收、格挡反击；受控延迟条件与分析尚未实现。 |
| F4 信息驱动的计划修正 | 获取线索，判断未知通路，返程利用先前发现 | 信息接收、可避免的重复探查和完成情况；预先给明信息的对照 | 复用纸条、居民指路、侦察；按需补变体与历史证据。 |
| F5 分布式回收协作 | 两个同等 Agent 分处不同位置、拥有不同局部信息或资源，自主决定分工与会合 | 共同交付与存活；相同人数和预算的无聊天／共享信息团队 | 多人底座已有；真正影响决策的信息布局和任务评分仍需设计。 |
| F6 经验利用与情境迁移 | 前段接触原生移动、交互或遭遇模式，后段在新位置／朝向／情境中应用 | 后段错误与资源成本、匹配的经验机会对照；控制装备、生命、熟悉度与时间影响 | 需要新的完整 Episode 任务和阶段证据，尚无已验证学习评分器。 |
| I1 单人综合远征 | 筹备、发现通路、战斗或取货、保留余量返程 | 整项成功与有证据的阶段结果，配套独立技能诊断 | 复用据点、市场或共享燃料跨越；不拼接互不相关的小任务。 |
| I2 团队综合远征 | 分布式侦察／筹备、有时限的回收、共同返程 | 显式团队条件与通信对照；综合成绩独立报告 | 复用原生团队与物资；团队遭遇／合同事件评分不能自动继承单人实现。 |

空间任务不只有走到坐标，也可以是搭出真正可用的跨越结构、找到可交互的视角、取得满足射线／站位条件的位置。协作任务应让 Agent 自己决定谁做什么，而不是照着规定话术和角色脚本执行；不能靠聊天次数得分。优先使用普通地形、原生物品／线索、掉落物和聊天，不为了强迫协作设置人为角色锁或修改 NPC 规则。

局内学习候选可以让前段经验帮助后段调整跨缝移动时长、不同朝向下的交互站位或类似敌人的应对。**保持原生规则一致，改变应用情境**。只记住一个坐标主要属于信息利用；后段更容易、装备更好或只留下前段幸存者，都可能伪造“学习效果”。应控制或报告这些因素，保留前段失败；无法区分时只能报告探索性指标或测量未完成。可以用独立 Episode 设置诊断对照，但被测学习轨迹本身始终在一局内，Agent 不跨对照局继承经验。

### 13.3 雷达图与维度成绩

雷达图展示**能力导向任务表现**，不是声称已经分离出六种纯能力。当前主要分数仍是有原生依据的任务成功／失败；不能从一个综合任务总分推导六个分数。

拟议聚合顺序是：重复 Episode → 任务变体 → 任务族 → 维度。先固定成员、变体、重复次数、预算和权重，再做验证性实验；任务族等权只是待审阅建议，尚未实现为排行榜规则。优先报告每个游戏／赛道的成绩，跨游戏汇总必须明确权重，不能让某款游戏的近似任务更多就占更大份额。

综合任务另列成绩，辅助标签不重复加分。阶段分必须有公开、可核验的任务专属规则，本次不增加通用的“完成一半就给一半分”。图旁同时展示任务族与 Episode 数、置信范围和缺失覆盖；同场景变体与重复运行具有相关性，不能简单当作大量独立题目。只有一个任务族的维度成绩应标为初步结果，不能包装成全面能力量表。

合法游戏失败可以为零分；基础设施失败、证据缺失、Benchmark 尚未实现的维度不能记 Agent 零分。若 Agent 确实无法参与已支持、已公布的评测协议，可以按事先规定的准入规则记零，但必须与基础设施故障区分。缺失轴不得悄悄重归一化成看似完整、可比的六边形。

延迟、成本、死亡、资源消耗与通信行为作为辅助诊断另外报告。多人条件要披露人数、每角色及团队合计推理资源、墙钟与比较预算；两人比单人更好可能只是增加了一个行动者，不能直接当作沟通收益。优先用同人数的无聊天／共享信息团队作解释性对照。

### 13.4 后续落地顺序

1. 盘点现有任务的主／辅需求、实际评分证据、原生机制、工具代劳与赛道缺口，标记保留、改造、仅诊断或暂缓；历史 ID 与结果不动。
2. 审阅 60 个主测／10 个综合候选的设计清单及各自能支持的主张；用早期八族切片安排渐进开发，优先考虑 F5/F6 缺口，不承诺所有候选立即实现。
3. 确认后再实现最小元数据与选集字段，不改底层生命周期，也不移动目录。
4. 只按需要实现变体与证据；涉及迁移、阶段、玩家交易或团队事件的新要求，先核验原生能力与协议。
5. 用有界 Baseline 做准入赛道验收，原生可行性／通信另作诊断；保留失败，检查对照是否真的区分目标需求。
6. 根据实验校准预算和难度，修正不成立的解释，再冻结紧凑任务分布与分析方案、扩大模型／Agent 范围；不为了任务数量或预期排名扩张目录。

本次只更新设计，不修改任何任务 YAML、六维评分器或运行结果，不启动新的模型／游戏评测或云端作业。
